## 三、真实失败案例与修复过程

### 失败案例 1：口语化表达 "卡得要死" 未命中知识库



* **输入**：T09 描述 "这台电脑卡得要死，点个半天才反应，风扇还呼呼响"。

* **预期结果**：应匹配到知识库 #7「电脑运行卡顿 / 磁盘满」，类别为 "电脑主机故障"。

* **实际结果（修复前）**：


  * 类别被判为 **"其他"**；

  * AI 建议输出 "知识库中未找到高匹配条目"；

  * 工单没有给出任何排查建议。

* **问题原因**：知识库 #7 的关键词只写了书面词 "卡顿、很卡、慢、反应慢、风扇响"，没有覆盖学生口语 "卡得要死、卡、点半天、风扇呼呼响"。`"卡得要死"` 不包含 `"卡顿"` 这个连续子串，因此得分为 0。

* **修改过程**：在 `knowledge_base.py` 第 #7 条 keywords 中补充口语化同义词：



```
"卡得", "卡得要死", "卡死", "点半天", "好卡", "风扇呼呼"
```



* **修改后结果**：重新灌入 T09，命中关键词 "卡得、点半天、风扇呼呼"，得分 9，正确归类为 "电脑主机故障"，并给出 "任务管理器查看占用、清理 C 盘" 等建议。✅

### 失败案例 2：极短描述 "老样子" 未触发人工确认



* **输入**：T10 描述仅 "老样子" 三个字。

* **预期结果**：描述严重不足，应标记 `need_manual=1` 并提示 "故障描述过短"。

* **实际结果（修复前）**：


  * 早期版本 `ai_engine.py` 只在 "知识库无匹配" 时才置位 `need_manual`；

  * 由于 "老样子" 碰巧命中了某条目的 1 个低权重关键词，系统认为 "有匹配"，**未标记需人工确认**；

  * 管理员在工单列表里看不到任何提醒，可能直接按建议处理，导致误判。

* **问题原因**：缺少 "信息完整性" 维度的检查 —— 只看了知识库命中分，没看描述本身是否提供了有效信息。

* **修改过程**：在 `ai_engine.py` 新增 `_detect_info_missing()` 函数：


  * 必填字段（报修人 / 设备 / 位置 / 联系方式）为空 → 记录问题；

  * 描述长度 < 5 字 → 记录 "故障描述过短"；

  * 描述只含标点 / 问号 → 记录 "无实质内容"；

  * 只要存在任意问题，`need_manual` 强制置 1。

* **修改后结果**：T10 入库后 `need_manual=True`，详情页明确列出 "故障描述过短（3 字），无法判断现象"，管理员看到提示后联系报修人补充了 "显示器闪了一下就黑了"。✅

## 四、统计口径说明



* 工单总数、各类别数量、各状态数量均来自 `database.stats()`，与 SQLite 实际行数一致；

* 紧急程度 "高" 仅在命中高优词（急 / 实验课 / 答辩 / 立即等）时给出，避免滥用；

* "需人工确认" = 信息缺失 **或** 知识库无匹配 **或** 紧急度为高，三个条件任一成立即置位。

## 五、结论

12 条模拟工单 + 3 条异常输入全部按预期通过；2 个真实失败案例已完成定位、修复与回归。系统形成了 **报修提交 → 数据库保存 → AI 分析 → 知识库建议 → 人工处理 → 状态更新** 的完整业务闭环。
