## 二、失败案例 1：口语化表达"卡得要死"未命中知识库（缺陷①）

- **输入**：T09 描述"这台电脑卡得要死，点个半天才反应，风扇还呼呼响"。
- **预期结果**：应匹配到知识库 #7「电脑运行卡顿/磁盘满」，类别为"电脑主机故障"。
- **实际结果（修复前）**：
  - 类别被判为 **"其他"**；
  - AI 建议输出"知识库中未找到高匹配条目"；
  - 工单没有给出任何排查建议。
- **问题原因**：第一版 `knowledge_base.py` 第 #7 条的口语化关键词被删除，只保留书面词"卡顿、很卡、慢、反应慢、风扇响"，没有覆盖学生口语"卡得要死、点半天、风扇呼呼响"。"卡得要死"不包含"卡顿"这个连续子串，因此得分为 0。
- **排查过程**：用 T09 单独跑 `ai_engine.analyze()`，发现 `search()` 返回空列表；逐条打印知识库 #7 的关键词命中情况，确认口语词全部缺失。
- **修改过程**：在 `knowledge_base.py` 第 #7 条 keywords 中恢复口语化同义词：
  ```python
  "好卡", "卡得", "卡得要死", "卡死", "点半天", "风扇呼呼"
  ```
- **修改后结果**：重新灌入 T09，命中关键词"卡得、点半天、风扇呼呼"，得分 9，正确归类为"电脑主机故障"，并给出"任务管理器查看占用、清理 C 盘"等建议。✅

## 三、失败案例 2：极短描述"老样子"未触发人工确认（缺陷②）

- **输入**：T10 描述仅"老样子"三个字。
- **预期结果**：描述严重不足，应标记 `need_manual=1` 并提示"故障描述过短"。
- **实际结果（修复前）**：
  - 第一版 `ai_engine.py` 中 `need_manual` 只在紧急度为"高"时置位（`need_manual = 1 if (urgency == "高") else 0`）；
  - 信息缺失、知识库无匹配均不再触发；
  - 管理员在工单列表里看不到任何提醒，可能直接按建议处理，导致误判。
- **问题原因**：缺少"信息完整性"维度的检查——只判断了紧急度，没有检查描述本身是否提供了有效信息。
- **排查过程**：对 T10、T11 分别跑 `analyze()`，发现 `info_problems` 恒为空列表、`need_manual` 恒为 0；对照代码确认信息完整性检查函数被移除、`need_manual` 判定条件被简化。
- **修改过程**：在 `ai_engine.py` 新增 `_detect_info_missing()` 函数：
  - 必填字段（报修人/设备/位置/联系方式）为空 → 记录问题；
  - 描述长度 < 5 字 → 记录"故障描述过短"；
  - 描述只含标点/问号 → 记录"无实质内容"；
  - 判定规则改为：`need_manual = 1 if (info_problems or not matched or urgency == "高") else 0`。
- **修改后结果**：T10 入库后 `need_manual=True`，详情页明确列出"故障描述过短（3字），无法判断现象"；T11（知识库外）同样正确标记人工确认。✅

## 四、失败案例 3：紧急故障被判为"低"紧急（缺陷③）

- **输入**：T01 描述"今天实验课要用，板子下载不进去程序，串口也没反应，急！"
- **预期结果**：紧急度"高"、需人工确认"是"。
- **实际结果（修复前）**：紧急度判为 **"低"**，需人工确认 **"否"**——管理员无法第一时间发现实验课前的紧急故障。
- **问题原因**：第一版 `URGENT_HIGH_WORDS` 高优词表被删去了"急、紧急、实验课、答辩"等核心词，仅剩"立即、马上"等，T01 的"急、实验课"均未命中。
- **修改过程**：恢复高优词表：
  ```python
  "急", "紧急", "立即", "马上", "实验课", "答辩", ...
  ```
- **修改后结果**：T01 紧急度正确判为"高"，同时由于紧急度为高自动置位 `need_manual=1`。✅

## 五、失败案例 4：工单状态更新不生效（缺陷⑥）

- **操作**：在工单管理页选择一条工单，将状态改为"处理中"并填写处理结果，点击保存。
- **预期结果**：列表状态变为"处理中"。
- **实际结果（修复前）**：处理结果保存成功，但**状态始终是"待处理"**，界面没有任何报错。
- **问题原因**：第一版 `database.py` 的 `update_status()` SQL 语句遗漏了 `status` 字段：
  ```sql
  -- 第一版（错误）
  UPDATE workorders SET result = ?, updated_at = ? WHERE id = ?
  -- 最终版（正确）
  UPDATE workorders SET status = ?, result = ?, updated_at = ? WHERE id = ?
  ```
  SQL 语法合法、能执行成功，但 `status` 列未被更新，属于"静默失败"，排查难度大。
- **排查过程**：修改状态后直接查库（`SELECT status FROM workorders WHERE id=?`），发现 `status` 未变而 `result` 已更新；对比 `create_workorder` 的插入字段，发现 `update_status` 少了 `status = ?` 参数绑定。
- **修改过程**：在 SQL 语句中补回 `status = ?` 并传入参数。
- **修改后结果**：状态可正常流转"待处理 → 处理中 → 已完成"。✅

## 六、附加异常输入缺陷（④⑤）

| 缺陷 | 现象 | 修复 | 结果 |
| ---- | ---- | ---- | ---- |
| ④ 空描述不校验 | E1 空描述可直接提交入库 | 恢复必填校验 `if not description.strip(): missing.append("故障描述")` | ✅ 提示"请填写必填项：故障描述"，不入库 |
| ⑤ 摘要不截断 | E3 超长描述摘要完整输出不截断 | `snippet = desc[:40] + ("…" if len(desc) > 40 else "")` | ✅ 摘要截取前 40 字并加"…" |

## 七、统计口径说明

- 工单总数、各类别数量、各状态数量均来自 `database.stats()`，与 SQLite 实际行数一致；
- 紧急程度"高"仅在命中高优词（急/实验课/答辩/立即等）时给出，避免滥用；
- "需人工确认" = 信息缺失 **或** 知识库无匹配 **或** 紧急度为高，三个条件任一成立即置位。

## 八、结论

第一版 6 处缺陷全部完成定位、修复与回归测试：12 条测试工单由 **4 条失败 → 全部通过**，3 个界面缺陷全部修复。系统形成了 **报修提交 → 数据库保存 → AI 分析 → 知识库建议 → 人工处理 → 状态更新** 的完整业务闭环。
